# College upgrade: temporal validation, recent form, and presentation

This version implements upgrades **1 and 2** from the review, plus the syllabus additions: **ordinary least-squares regression, linear support-vector regression, and learning curves**. A local Streamlit front end presents the actual saved predictions. It does not require an API key, internet connection during the demonstration, or retraining when opened. For future sports expansion, see [MULTISPORT_FEASIBILITY.md](MULTISPORT_FEASIBILITY.md).

## Run the project

From the directory containing this guide, with Python 3.12 or newer:

```powershell
python -m pip install -r requirements.txt -r requirements-dashboard.txt
python run_pipeline.py
python -m streamlit run dashboard.py
```

Open **http://localhost:8501**. `python run_upgrade.py` is an equivalent direct entry point for the new experiment. You can open the dashboard immediately when `models/upgraded/` already contains a completed run.

On Windows, you can also double-click `start_dashboard.cmd` after dependencies are installed. Keep its terminal open during the demo; stop it with Ctrl+C. If port 8501 is already serving this dashboard, open the existing page instead of starting another copy.

The included `.venv` is a Unix-style environment from the original project and is not a Windows interpreter. Use your working Python installation or create a fresh Windows environment. The run manifest records the actual packages used; installing the pinned requirements and reproducing in a fresh environment is a separate verification step.

For a development smoke run, use `python run_upgrade.py --quick`. It writes to **models/upgraded_smoke/** and never replaces presentation results. Use `--rebuild-features` to force regeneration. Otherwise, the window cache is reused only if hashes of the base table, appearances and feature-builder code match.

The original experiment remains available through `python run_pipeline.py --legacy`. Its original artifacts, README tables and notebook are retained as the earlier benchmark, including its documented limitations. The new dashboard reads only **models/upgraded/**.

## What changed

**Validation and inference**

- `src/temporal.py` creates expanding calendar folds: train before 2020 and validate 2020; train before 2021 and validate 2021; train before 2022 and validate 2022. Every training date strictly precedes every validation date. Same-day observations cannot cross a boundary.
- `src/preprocessing.py` fits height medians, exposure-weighted position priors, numeric imputation, category vocabulary and optional scaling only on the training rows of each fold. Unseen categories are handled at inference.
- `src/upgraded_training.py` uses the same XGBoost constructor for validation and final fitting: 250 trees, learning rate 0.06, histogram trees, seed 42, and the same regularization/sampling settings. Depth 5 versus 7 is selected on mean validation log RMSE separately for each feature set.
- The complete feature-transformer/encoder/model pipeline is saved with joblib. Reloaded XGBoost predictions are checked against the in-memory predictions on 128 rows. Load only the trusted artifacts generated by this project.
- Final models train on all valuations before 2024, with 2024 onward used for the existing historical evaluation. No independent calibration is needed because these upgrades do not add smearing or prediction intervals. The old test period has already been inspected and is explicitly not described as a newly blind holdout.

**Recent form and observation coverage**

- `src/recent_features.py` aggregates per-player daily match records and uses cumulative totals plus strict ASOF joins to build **90-, 180- and 365-day** windows.
- Each window includes its starting boundary and excludes the valuation date: `[valuation_date - window, valuation_date)`.
- Inputs include recorded minutes, appearances, goals, assists, days since the last captured match, length of observed history, and flags for prior appearances and recent playing time.
- Recent 90-day minutes and smoothed output rates are compared with the preceding, non-overlapping 90-day period. This avoids comparing raw counts from unequal-length windows.
- Per-90 output is shrunk toward a position-level training prior with 450 pseudo-minutes. That fixed strength is a declared initial choice, not a test-tuned optimum. A zero-exposure estimate equals a prior and is accompanied by observation indicators; it is not presented as measured player output.
- Recomputed annual minutes/goals/assists must match the existing base table. Duplicate appearance IDs and duplicate player-game rows are rejected.

These flags describe **what the dataset observed**. They cannot prove whether an absent player was injured, benched, or playing in an uncovered competition. Historical club/league attribution and snapshot position/height/foot remain limitations. The model still has no prior market-value inputs.

## The experiments and artifacts

Five models share the same 111,706 historical test rows and use all 435,947 pre-2024 training observations in their final fit:

1. **Corrected annual-feature XGBoost:** a baseline with repaired preprocessing and calendar validation.
2. **Recent-form XGBoost:** adds the recent windows, trends and coverage signals.
3. **Recent-form Ridge:** sees the same engineered input columns as model 2, with scaling and fixed alpha 100.
4. **Ordinary least squares (OLS):** unregularized linear regression on log market value, with the same recent-form inputs and standardization. This directly demonstrates the least-squares criterion from Unit III.
5. **Linear support-vector regression:** `LinearSVR`, with standardized inputs, squared epsilon-insensitive loss, epsilon 0.1 in log-value units, and C selected from 0.01/0.1/1 on the original calendar folds. Convergence warnings stop training rather than being ignored. This demonstrates Unit IV's support-vector regression.

The SVR is linear, not RBF-kernel SVR. This choice permits a full-data comparison; scikit-learn documents that [LinearSVR scales better to large sample counts](https://scikit-learn.org/stable/modules/generated/sklearn.svm.LinearSVR.html), whereas [kernel SVR has more-than-quadratic fit-time complexity](https://scikit-learn.org/stable/modules/generated/sklearn.svm.SVR.html). No subsampling or kernel approximation is hidden in the final model comparison. A kernel experiment on a matched subset can be a later extension.

The annual baseline includes a missing-height flag as part of the preprocessing repair, so it is not an exact replay of the original feature matrix. The old headline numbers should not be used as a controlled estimate of the recent-feature effect. Compare models 1 and 2 for that purpose. Both XGBoost variants receive the same search budget. The headline recent-form model is fixed by experiment design; the test set does not choose the winner. If new features make a metric worse, that result remains visible.

## Learning curves and syllabus interpretation

The dedicated dashboard page varies training size across **5%, 20%, 50% and 100%** of the 378,379 pre-2023 observations while keeping the **57,568 observations in 2023** fixed for validation. Samples are nested random draws with seed 42 from the earlier training pool; all samples remain strictly before the validation dates. Random sampling *inside this already historical pool* does not mix future labels into training. It also avoids a moving training cutoff being mistaken for a pure sample-size effect.

For each sample size, all four models refit preprocessing and parameters from scratch. XGBoost depth and SVR C are fixed at settings selected using 2020–2022 validation, so 2023 and 2024 onward do not choose them. This produces 16 fitted curve points. The final headline comparison separately fits on all data through 2023 and evaluates 2024 onward; do not confuse curve scores with final test scores.

- **Training much better than validation:** possible overfitting, but time drift or cohort differences can also contribute.
- **Both errors high and plateauing:** possible underfitting, insufficient features or irreducible target noise.
- **Validation error falling with more observations:** evidence that more training data helps for this configuration.

This is one seeded diagnostic experiment, not confidence intervals or an exact statistical bias–variance decomposition. Repeated players across time are intentional for returning-player prediction. OLS/Ridge/SVR are linear in the engineered inputs, which already contain age-squared and interaction terms. They are not restricted to a straight line against raw age alone.

## Demonstration script for the professor

Allow about five minutes:

1. **Overview:** explain the target is a Transfermarkt valuation, not an actual transfer fee. Show the observed result of adding recent form, including any metric that did not improve.
2. **Coverage:** use the league/position filters to demonstrate why a dataset can contain zero minutes without proving the player did not play.
3. **Player explorer:** search a familiar player, select a historical valuation date and compare the actual reference with the model estimate. Explain that the reference is shown for retrospective evaluation, not used as an input.
4. **Recent-form inputs:** show the 90/180/365-day table and describe how recent and preceding 90-day periods produce a trend. These are inputs, not explanations of exactly how much each changed the prediction.
5. **Learning curves:** compare OLS or linear SVR with XGBoost and explain training error, validation error and the gap.
6. **Method & caveats:** show the calendar split table, training-only preprocessing and saved run details. End with one clear limitation and the next experiment you would run.

The interface includes position/league filters, searchable player selection, historical date selection, line/bar charts, empty states, coverage warnings and CSV/manifest downloads. It displays saved backtest estimates, not a live scouting service. No prediction intervals are shown because none have been calibrated in this scope.

## What is achievable in 48 hours?

The implementation in this version supplies the validation repair, recent-form engineering and basic presentation layer. A realistic remaining 48-hour sprint should choose one substantive extension, then reserve time for validation and presentation. Do not attempt every item below.

| Budget | Task | Value |
|---|---|---|
| Hours 0–8 | Reproduce this run, inspect coverage, verify data provenance and select contrasting cases | Confidence in the baseline and the claims |
| Hours 8–18 | Add strictly lagged previous value and valuation age; compare persistence against a history-informed model | Stronger practical baseline and research question |
| Hours 18–30 | Choose **either** grouped feature ablations **or** a small dated-text pilot if text is already available | Evidence about which information helps |
| Hours 30–40 | Add Tree SHAP explanations for 4–6 cases; rehearse the dashboard | An understandable account of successes and failures |
| Hours 40–48 | Freeze outputs, test on the actual presentation laptop and prepare slides | A reliable presentation |

Other independent options: prediction intervals (roughly 8–14 focused hours, including a new calibration split and coverage analysis), a narrow randomized parameter search (4–8 hours), or richer lineup-based usage features (6–10 hours). These are estimates rather than guaranteed timings. A polished dashboard alone is presentation work; the validation fixes and controlled experiments are the ML contribution.

## Is multimodal realistic?

**Yes, tabular statistics plus natural-language scouting/news text is a defensible small multimodal extension.** The current model is tabular. It should not be described as multimodal until an independent second information source is actually used and evaluated.

The most feasible architecture is:

```text
Historical performance statistics ──> tabular model ──┐
                                                    ├─> fused prediction
Dated scouting/news text ───────────> text encoder ───┘
```

Start with training-only TF–IDF and regularized regression as a transparent text baseline. If time permits, use a frozen sentence encoder and combine compact text vectors with numeric features, or combine separately trained model predictions using weights learned on development data. Sentence Transformers supports fixed text embeddings through `encode`; see the [official usage guide](https://sbert.net/docs/sentence_transformer/usage/usage.html). A pretrained encoder avoids training a language model from scratch, but does not remove data-provenance or evaluation requirements.

The local CSVs do not provide a verified historical scouting-report corpus. There is an image URL in the player table and text in event records, but neither is a ready, aligned scouting-text dataset. Event descriptions mostly describe already counted events and require an incremental-information check. The bottleneck is collecting and matching useful historical text, not constructing the fusion layer.

For a 48-hour pilot:

- Use a narrow, explicitly scoped cohort and obtain enough independently dated reports to evaluate meaningfully. A few hand-picked examples can demonstrate a pipeline, but cannot establish general predictive improvement.
- Store `player_id`, `published_at`, `source_url`, `text`, and provenance/reuse notes. Require a publication timestamp strictly before the relevant valuation. Do not backdate current reports.
- Exclude or redact explicit valuations, transfer fees and other target-revealing material. Review the resulting text, since removing currency symbols alone does not remove every target clue.
- Deduplicate copied articles. Fit text vocabulary, dimensionality reduction, fusion weights and all numeric transforms on development training data only. Use chronological validation, and document that a pretrained encoder may have its own later training cutoff.
- Compare **statistics-only**, **text-only**, and **fused** models on the **same text-covered rows**. Also report coverage and fallback performance on the full population, so a convenient article-covered cohort cannot silently replace the original task.
- Report data size and uncertainty honestly. A result with no improvement is valid evidence; showing a text box or a photo is not evidence of multimodal learning.

Do not use portraits to infer ability or market value; they are likely to add identity shortcuts and irrelevant appearance information. A chatbot, voice input, generated match summary, or image displayed beside a prediction may improve the interface but does not itself make the valuation predictor meaningfully multimodal. Video-based football analysis would require footage alignment, feature extraction and substantially more validation; it is a poor fit for this deadline.

**Best 48-hour choice:** complete a strong history baseline and explain the existing model. Choose a text-fusion pilot only if verified dated text is already obtainable within the first few hours. Otherwise, present it as a carefully designed next step rather than a completed feature.

## Tests

```powershell
python -m pip install -r requirements-dev.txt
python -m pytest tests/test_upgrades.py -q
python -m pytest tests/test_dashboard.py -q
python tests/check_consistency.py
```

The new tests exercise exact historical-window boundaries, same-day/future exclusion, missing history, duplicate input rejection, date-grouped folds, training-only preprocessing, unknown categories, shrinkage and serialization. The old consistency check continues to validate the preserved legacy artifacts. Dashboard interaction tests are in `tests/test_dashboard.py` and require completed upgraded artifacts.

The design follows scikit-learn's guidance to [fit preprocessing inside the training pipeline](https://scikit-learn.org/stable/common_pitfalls). Final results and runtime belong in the generated run manifest rather than manually copied here.
